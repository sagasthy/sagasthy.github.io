EX 01
Create a Multi-Stage YAML Pipeline
Azure Pipelines YAML
Lab Task

You need to create a YAML pipeline in Azure DevOps with three sequential stages: Build, Test, and Deploy. The Test stage must only run if Build succeeds. The Deploy stage must only run if Test succeeds. The pipeline must trigger on pushes to main.

Step-by-Step Answer
  1. Go to Azure DevOps → Pipelines → New PipelineSelect your repo (Azure Repos Git or GitHub). Choose "Starter pipeline" or "Existing YAML file".
  2. Create azure-pipelines.yml in your repo rootAdd the following YAML:
trigger:
  branches:
    include:
      - main

stages:
  - stage: Build
    jobs:
      - job: BuildJob
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "Building..."

  - stage: Test
    dependsOn: Build
    condition: succeeded()
    jobs:
      - job: TestJob
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "Testing..."

  - stage: Deploy
    dependsOn: Test
    condition: succeeded()
    jobs:
      - job: DeployJob
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "Deploying..."
  1. Commit and push to mainThe pipeline triggers automatically. Verify all three stages appear in sequence in the pipeline run view.
  2. Verify stage dependencyManually fail the Build stage by changing the script to exit 1. Confirm that Test and Deploy are skipped.
MCQ Version
Your YAML pipeline has Build → Test → Deploy stages. The Test stage has dependsOn: Build and condition: succeeded(). The Build stage fails. What happens to the Test and Deploy stages?
A Both run — explicit conditions override failure behaviour
B Both are skipped — succeeded() evaluates to false when Build fails
C Test runs, Deploy is skipped
D Both fail immediately when they start
B is correct. succeeded() is the default condition — it returns false if any dependency stage failed, causing the dependent stage to be skipped (not failed). Skipped is a distinct state from failed in Azure Pipelines. The Deploy stage also skips because its dependency (Test) was skipped, not succeeded.
⚠ Exam Trap
A skipped stage does not cause the overall pipeline to fail. The pipeline may be marked "partially succeeded" rather than "failed". Know the difference between skipped, failed, and cancelled stage states.
EX 02
Configure Pipeline Environments with Approvals
Azure Pipelines Environments
Lab Task

Create an Azure Pipelines environment named production. Configure it to require approval from a specific user before any deployment job targeting that environment can proceed. Update your pipeline to use a deployment job targeting this environment.

Step-by-Step Answer
  1. Create the EnvironmentAzure DevOps → Pipelines → Environments → New environment. Name: production. Resource: None.
  2. Add Approval CheckClick the environment → Approvals and checks → + Add → Approvals. Add the approver's name. Save.
  3. Update pipeline YAML to use a deployment job
- stage: Deploy
  jobs:
    - deployment: DeployApp   # deployment: not job:
      environment: production    # references the environment
      pool:
        vmImage: ubuntu-latest
      strategy:
        runOnce:
          deploy:
            steps:
              - script: echo "Deploying to production"
  1. Trigger the pipeline and observeWhen the Deploy stage starts, the pipeline pauses and sends an approval notification. The approver must approve in the Azure DevOps UI before the deployment job executes.
MCQ Version
You want a human to approve deployments to production in an Azure Pipelines YAML pipeline. Which combination is required?
A Add an if condition checking Build.RequestedFor on the Deploy stage
B Use a classic release pipeline — YAML pipelines don't support approvals
C Create an Environment with an Approvals check, then target it from a deployment: job
D Add a gate: keyword to the Deploy stage YAML
C is correct. YAML pipelines fully support approvals via Environments. The key is using deployment: (not job:) which integrates with the environment. The gate: keyword does not exist in YAML. Classic pipelines are not required — YAML has equivalent functionality.
⚠ Exam Trap
You must use deployment: not job: to target an environment. A regular job: with an environment: property does not exist — only deployment jobs integrate with environments in YAML.
EX 03
Configure Branch Policies and PR Validation
Azure Repos Branch Policies
Lab Task

Protect the main branch in an Azure DevOps repo. Requirements: at least 2 reviewers, a passing build validation pipeline, and no direct pushes. Ensure the build validation pipeline runs on every PR targeting main.

Step-by-Step Answer
  1. Navigate to branch policiesAzure DevOps → Repos → Branches → hover over main → click the "..." menu → Branch policies.
  2. Enable Require a minimum number of reviewersSet minimum to 2. Enable "Reset votes when new changes are pushed" for stricter control.
  3. Add Build ValidationUnder "Build Validation" → + Add. Select your pipeline. Set trigger to "Automatic". Set policy requirement to "Required". Save.
  4. Block direct pushesBranch policies automatically block direct pushes when any required policy is set. Verify by attempting a direct push — it should be rejected.
  5. Test with a PRCreate a feature branch, make a change, open a PR targeting main. The build validation pipeline should trigger automatically.
MCQ Version
A developer pushes directly to main bypassing the PR process. Which Azure DevOps configuration prevents this?
A Pipeline YAML trigger exclusion on main
B Setting the developer's permissions to "Contribute" instead of "Admin"
C Enabling branch policies on main with at least one required policy
D Adding a pre-commit hook in the repository
C is correct. Branch policies in Azure DevOps enforce that all changes go through a PR. When any required policy is active, direct pushes to the branch are blocked at the server side — no client-side hook needed. Trigger exclusions only affect pipeline runs, not who can push.
EX 04
Create an Azure Artifacts Feed and Publish a Package
Azure Artifacts NuGet
Lab Task

Create an Azure Artifacts feed named internal-packages scoped to your project. Configure a pipeline to restore NuGet packages from this feed. Add an upstream source pointing to NuGet.org so packages not in your feed are fetched transparently.

Step-by-Step Answer
  1. Create the FeedAzure DevOps → Artifacts → Create Feed. Name: internal-packages. Scope: Project. Enable upstream sources (NuGet Gallery). Click Create.
  2. Connect to FeedClick "Connect to feed" → NuGet.exe or dotnet. Copy the feed URL — it looks like: https://pkgs.dev.azure.com/{org}/{project}/_packaging/internal-packages/nuget/v3/index.json
  3. Add NuGetAuthenticate task to pipeline
steps:
  - task: NuGetAuthenticate@1   # Authenticates to Azure Artifacts feeds

  - task: NuGetCommand@2
    inputs:
      command: restore
      feedsToUse: select
      vstsFeed: internal-packages   # Feed name
  1. Understand feed viewsNavigate to Artifacts → internal-packages. Packages appear in the @local view by default. Promote a package to @release view by selecting it → Promote.
MCQ Version
Your pipeline restores NuGet packages from an Azure Artifacts feed. A required package exists on NuGet.org but not in your feed. You have upstream sources enabled. What happens?
A The restore fails — packages must be manually uploaded to the feed first
B The package is fetched from NuGet.org through the upstream source and saved in the feed for future use
C The pipeline prompts the developer to approve the external package download
D The package is fetched directly from NuGet.org, bypassing the feed entirely
B is correct. Upstream sources act as a transparent proxy — when a package is not found locally, Azure Artifacts fetches it from the configured upstream (NuGet.org) and saves a copy in your feed. Subsequent requests are served from the feed cache, giving you control and visibility over all dependencies used in your organization.

Configure Variable Groups and Link to Azure Key Vault
Azure Pipelines Key Vault
Lab Task

Create a variable group named release-secrets linked to an Azure Key Vault. Map two secrets from the vault to pipeline variables. Configure pipeline permissions so only your release pipeline can use this variable group. Reference the secrets in a YAML pipeline.

Step-by-Step Answer
  1. Create Variable GroupAzure DevOps → Pipelines → Library → + Variable group. Name: release-secrets. Toggle "Link secrets from an Azure key vault as variables". Select your subscription and Key Vault.
  2. Map secretsClick "+ Add" under variables. Select the secrets you want to map (e.g., API-KEY, DB-PASSWORD). Save.
  3. Restrict pipeline accessIn the variable group → Security tab → Pipeline permissions → change to restricted. Explicitly add only your release pipeline.
  4. Reference in YAML pipeline
variables:
  - group: release-secrets   # Reference the variable group

steps:
  - script: echo "API key length: ${#API_KEY}"
    env:
      API_KEY: $(API-KEY)   # Secret masked in logs automatically
MCQ Version
You have a variable group linked to Azure Key Vault. A junior developer creates a new pipeline that references the same variable group. What happens?
A The new pipeline automatically has access — all pipelines in the project share variable groups
B If the variable group is set to restricted access, the new pipeline is blocked until explicitly authorized
C The Key Vault access policy blocks the new pipeline at the Azure resource level
D The pipeline runs but secrets are returned as empty strings
B is correct. Pipeline permissions on variable groups control which pipelines can use them within Azure DevOps. When restricted, unauthorized pipelines are blocked before the pipeline even runs — the developer will see an authorization error in the pipeline UI and must request access.
EX 06
Create and Use Reusable YAML Templates
Azure Pipelines Templates
Lab Task

Create a reusable YAML step template that runs a security scan. Store it in a central repository. Reference this template from a pipeline in a different repository. The template should accept a parameter for the scan type.

Step-by-Step Answer
  1. Create the template file in central repoIn repo central-templates, create templates/security-scan.yml:
# templates/security-scan.yml
parameters:
  - name: scanType
    type: string
    default: full

steps:
  - script: echo "Running ${{ parameters.scanType }} security scan"
    displayName: Security Scan (${{ parameters.scanType }})
  1. Reference the template from another pipelineIn your consuming pipeline repo, add a resources block and use the template keyword:
resources:
  repositories:
    - repository: templates
      type: git
      name: MyProject/central-templates

stages:
  - stage: Build
    jobs:
      - job: BuildAndScan
        steps:
          - script: echo "Building..."
          - template: templates/security-scan.yml@templates
            parameters:
              scanType: quick
MCQ Version
Your organization wants all pipelines to mandatorily extend a centrally managed security template that cannot be bypassed. Which feature enforces this?
A CODEOWNERS file in each repository
B Allowed task policy at the organization level
C extends template with requireTemplate enforcement at organization or project level
D Branch policy requiring PR review on pipeline YAML files
C is correct. The extends keyword combined with requireTemplate creates a hard enforcement — pipelines that don't extend from the approved template are rejected at startup before any steps run. CODEOWNERS and branch policies are soft controls requiring human review. The allowed task policy controls which tasks can run, not whether templates are used.
EX 07
Create a GitHub Actions CI Workflow
GitHub Actions CI
Lab Task

Create a GitHub Actions workflow that triggers on push to main and on pull requests targeting main. The workflow must: checkout code, set up Node.js 20, install dependencies using npm ci, cache node_modules, and run tests with npm test.

Step-by-Step Answer
  1. Create .github/workflows/ci.yml in your GitHub repo
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'       # Built-in npm caching

      - name: Install dependencies
        run: npm ci          # Deterministic install

      - name: Run tests
        run: npm test
  1. Commit and push to main or open a PRThe workflow triggers. View it under Actions tab in GitHub. Green checkmark = all steps passed.
MCQ Version
Your GitHub Actions workflow uses actions/setup-node@v4 with cache: 'npm'. On the first run after adding this, what happens?
A Cache hit — packages are restored instantly
B Cache miss — npm install runs normally, then cache is populated for future runs
C The workflow fails — cache must be pre-populated before first use
D Caching is skipped on the first run automatically
B is correct. On first run, no cache exists for the computed key — this is a cache miss. The workflow runs npm install normally, and the cache is saved at the end of the run. All subsequent runs with the same key (same package-lock.json hash) get a cache hit and restore faster.
EX 08
Configure GitHub Environments with Required Reviewers
GitHub Actions Environments
Lab Task

Create two GitHub environments: staging and production. Add required reviewers to production only. Create a workflow with two sequential jobs — one deploying to staging and one to production. Each environment should have different secret values for API_KEY.

Step-by-Step Answer
  1. Create environments in GitHubRepo → Settings → Environments → New environment. Create staging (no protection rules). Create production → add Required reviewers → add your username. Save.
  2. Add environment-specific secretsIn each environment settings → Secrets → Add secret. Add API_KEY with different values for staging vs production.
  3. Create workflow with two deployment jobs
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: echo "Deploying to staging"
        env:
          API_KEY: ${{ secrets.API_KEY }}   # staging's value

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production   # pauses for approval here
    steps:
      - run: echo "Deploying to production"
        env:
          API_KEY: ${{ secrets.API_KEY }}   # production's value
MCQ Version
In a GitHub Actions workflow, two jobs target different environments with the same secret name DB_PASSWORD. Each environment has a different value configured. Which value does each job receive?
A Both jobs receive the repository-level secret value
B The first job's value — secrets resolve once at workflow start
C Each job receives its own environment's value — environment secrets are injected per job when that job starts
D The workflow fails — duplicate secret names across environments are not allowed
C is correct. Environment secrets are scoped to their environment and injected only when a job targeting that environment starts executing. This is what makes environment secrets valuable — the same secret name can hold different values per environment, and each job gets the right value automatically based on which environment it targets.
EX 09
Enable and Configure GHAS Secret Scanning with Push Protection
GitHub GHAS Security
Lab Task

Enable GitHub Advanced Security on a repository. Enable secret scanning and push protection. Test that a push containing a fake AWS access key is blocked. Review the secret scanning alerts dashboard.

Step-by-Step Answer
  1. Enable GHAS on the repositoryRepo → Settings → Security → Code security and analysis. Enable "GitHub Advanced Security" (required for private repos — free for public repos).
  2. Enable Secret ScanningIn the same Code security page → enable "Secret scanning". Then enable "Push protection" below it.
  3. Test push protectionCreate a test file containing a fake AWS-format key pattern (do NOT use real keys). Attempt to push. GitHub should block the push with a message identifying the secret type and location.
  4. Review alertsSecurity tab → Secret scanning alerts. All detected secrets appear here with their location, type, and status (open/resolved).
  5. Understand bypassPush protection can be bypassed by the developer with a documented justification. This creates an audit trail visible to admins.
MCQ Version
A developer tries to push a commit containing an API key. GHAS secret scanning is enabled with push protection. What is the outcome?
A The push succeeds and an alert is created post-push in the Security tab
B The push is permanently blocked and the developer must remove the secret before any push is possible
C The push is blocked with an error identifying the secret. The developer can bypass with a documented justification, creating an audit trail
D The secret is automatically redacted from the commit and the push succeeds
C is correct. Push protection blocks the push and requires the developer to take action — either remove the secret or provide a bypass justification. The bypass is not permanent silence; it creates an audit record. This is the key difference from detection mode (which only alerts after the push succeeds).
⚠ Exam Trap
Push protection is not an absolute block — it can be bypassed. The security value is the audit trail and the friction it adds, not an impenetrable barrier. Detection mode (no push protection) only alerts after the commit is already in the repository.
EX 16
Debug a Failing YAML Pipeline
Azure Pipelines Diagnostics
Lab Task

A pipeline is failing mid-run with a cryptic "Exit code 1" error and the default logs don't show why. Enable verbose agent diagnostics, read the structured log output to identify the root cause, and fix the pipeline. You must know which variable enables verbose logging and where to find agent diagnostic logs after a run.

Step-by-Step Answer
  1. Enable verbose logging via system.debugSet the pipeline variable system.debug to true. You can do this in three ways: add it as a pipeline variable in the UI, pass it as a runtime variable when queuing the run, or hardcode it in the YAML (remove before merging).
# Hardcode for a debug run — remove after diagnosing
variables:
  system.debug: true

steps:
  - script: ./build.sh
    displayName: Build
  1. Re-run the pipeline and read the verbose logsOpen the failing step in the pipeline run. With system.debug: true, each task logs every input, environment variable, and sub-command. Look for lines prefixed with ##[debug] — these show what the agent is actually executing.
  2. Download agent diagnostic logsIn the pipeline run view → three-dot menu → Download logs. The zip contains Worker_*.log per job. These include agent-level errors that never appear in the step UI — useful for infrastructure problems (proxy, network, disk space).
  3. Common root causes revealed by verbose loggingWrong working directory, missing environment variable, tool not on PATH, script line-ending issues (CRLF vs LF), or a task silently swallowing an error code.
  4. Fix and remove system.debugOnce the root cause is identified and fixed, remove system.debug: true — verbose logs significantly slow down runs and produce excessive output in production.
MCQ Version
A pipeline step fails with "Exit code: 1" and the standard logs show nothing useful. Which action provides the most detailed diagnostic output without modifying the pipeline YAML?
A Add set -x to every bash script in the pipeline
B Queue a new run and set the runtime variable system.debug to true
C Edit the agent's _diag folder configuration on the build server
D Enable "Verbose" in the pipeline's Triggers settings
B is correct. system.debug can be passed as a runtime variable when queuing a run — no YAML change required. It enables ##[debug] level output for every task, revealing exact inputs, environment variables, and sub-commands. Option A only helps for bash scripts you control, not for task-level issues. Option D doesn't exist.
⚠ Exam Trap
system.debug: true is not the same as agent.diagnostic: true. The former enables verbose task logging in the UI; the latter enables agent-level Worker logs (stored in the _diag folder on self-hosted agents, downloadable on Microsoft-hosted). Both are useful for different failure types.
EX 17
Add a Snyk Dependency Security Scan to a Pipeline
Snyk Security Azure Pipelines
Lab Task

Add a Snyk open-source dependency scan to an existing Azure Pipeline. The pipeline must fail the build if any high or critical severity vulnerability is found in the project's dependencies. Use a Snyk API token stored as a pipeline secret variable — never hardcoded in YAML. (Snyk is free for open-source public repos.)

Step-by-Step Answer
  1. Install the Snyk extensionGo to marketplace.visualstudio.com → search "Snyk Security" → Install into your Azure DevOps organisation. This adds the SnykSecurityScan@1 task.
  2. Create a Snyk API token secretSign up at snyk.io (free). Account Settings → API Token → copy. In Azure DevOps: Pipeline → Edit → Variables → Add variable named SNYK_TOKEN, paste the token, check Keep this value secret.
  3. Add the scan task to your pipeline
steps:
  - task: NodeTool@0      # Ensure correct runtime is present
    inputs:
      versionSpec: 20.x

  - script: npm ci         # Install deps so Snyk can read the lockfile

  - task: SnykSecurityScan@1
    displayName: Snyk — Dependency Vulnerability Scan
    inputs:
      serviceConnectionEndpoint: snyk-connection  # Or use token directly:
      testType: app
      severityThreshold: high     # Fail on HIGH or CRITICAL only
      failOnIssues: true
      monitorWhen: always         # Report to Snyk dashboard on every run

  - script: npm run build   # Only runs if Snyk scan passed
  1. Verify the gate worksIntroduce a known-vulnerable package version (e.g. lodash@4.17.4 in package.json) and push. The pipeline must fail at the Snyk step. Fix the version to the patched release and confirm the pipeline passes.
MCQ Version
You add SnykSecurityScan@1 with severityThreshold: high and failOnIssues: true to your pipeline. The scan finds 3 medium-severity and 1 high-severity vulnerabilities. What is the pipeline outcome?
A Pipeline passes — medium issues are reported but don't count against the threshold
B Pipeline fails — the 1 high-severity vulnerability meets the severityThreshold: high condition and failOnIssues: true triggers a build failure
C Pipeline fails — any vulnerability at any severity causes failure when failOnIssues: true
D Pipeline pauses and waits for a security team approval before continuing
B is correct. severityThreshold: high means Snyk only counts issues rated HIGH or CRITICAL toward the failure condition. The 3 medium vulnerabilities are reported but ignored by the gate. The 1 high-severity issue triggers failOnIssues: true, failing the pipeline. Option C is wrong — without a threshold, all severities would count, but a threshold explicitly narrows the scope.
⚠ Exam Trap
Dependencies must be installed (npm ci / pip install / etc.) before the Snyk task runs, or Snyk cannot read the resolved dependency tree. Running Snyk on the manifest alone (without a lockfile) may miss transitive vulnerabilities entirely.

EX 10
Deploy an Azure Web App via Azure Pipeline
Azure Web App Azure Pipelines
Lab Task

Create an Azure Pipeline that builds a web application and deploys it to an Azure App Service Web App using a service connection. The pipeline must use deployment slots — deploy to the staging slot first, then swap to production after a manual approval.

Step-by-Step Answer
  1. Pre-requisites in Azure PortalCreate an App Service Plan (Free F1 or Basic B1). Create a Web App. Add a deployment slot named "staging" (requires Standard tier or above).
  2. Create Service Connection in Azure DevOpsProject Settings → Service connections → New → Azure Resource Manager → Workload Identity Federation (recommended). Select subscription and resource group. Name it azure-connection.
  3. Create pipeline with slot deploy + swap
stages:
  - stage: DeployStaging
    jobs:
      - deployment: DeployToSlot
        environment: staging
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureWebApp@1
                  inputs:
                    azureSubscription: azure-connection
                    appName: my-web-app
                    deployToSlotOrASE: true
                    resourceGroupName: my-rg
                    slotName: staging

  - stage: SwapToProduction
    dependsOn: DeployStaging
    jobs:
      - deployment: SwapSlot
        environment: production   # approval gate here
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureAppServiceManage@0
                  inputs:
                    azureSubscription: azure-connection
                    action: Swap Slots
                    webAppName: my-web-app
                    resourceGroupName: my-rg
                    sourceSlot: staging
MCQ Version
What is the primary benefit of deploying to a staging slot before swapping to production in Azure App Service?
A It reduces deployment cost by using shared infrastructure
B The swap is near-instantaneous with no downtime, and the previous version remains in the staging slot for immediate rollback
C It automatically runs smoke tests before swapping
D It prevents the new version from receiving any traffic until explicitly enabled
B is correct. Slot swapping works by routing traffic between two warm instances — the swap is near-instantaneous (no cold start). The previous production version moves to the staging slot, enabling instant rollback by swapping back. This is the deployment pattern the AZ-400 exam associates with "minimizing downtime during deployments."
EX 11
Deploy Azure Infrastructure using Bicep via Pipeline
Bicep IaC Azure Pipelines
Lab Task

Write a Bicep template that creates an Azure Storage Account. Create an Azure Pipeline that deploys this Bicep template to a resource group using the AzureResourceManagerTemplateDeployment@3 task. Use Incremental deployment mode.

Step-by-Step Answer
  1. Create main.bicep in your repo
// main.bicep
param storageAccountName string = 'mystorageaccount${uniqueString(resourceGroup().id)}'
param location string = resourceGroup().location

resource storageAccount 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: storageAccountName
  location: location
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}

output storageAccountId string = storageAccount.id
  1. Create pipeline to deploy the Bicep template
steps:
  - task: AzureResourceManagerTemplateDeployment@3
    inputs:
      deploymentScope: Resource Group
      azureResourceManagerConnection: azure-connection
      subscriptionId: $(subscriptionId)
      action: Create Or Update Resource Group
      resourceGroupName: my-rg
      location: canadacentral
      templateLocation: Linked artifact
      csmFile: main.bicep
      deploymentMode: Incremental   # Only add/update, never delete
MCQ Version
Your Bicep deployment uses deploymentMode: Complete instead of Incremental. A storage account exists in the resource group that is NOT in the Bicep template. What happens?
A Nothing — Complete mode only adds resources, same as Incremental
B The deployment fails — Complete mode requires all resources to be in the template
C The storage account is deleted — Complete mode removes resources not defined in the template
D The storage account is moved to a different resource group
C is correct. Complete mode enforces the template as the desired state of the entire resource group — any resource in the group not present in the template is deleted. Incremental mode only adds or updates resources and never deletes. Use Complete mode carefully — it's useful for rollback scenarios but dangerous if your template doesn't capture all resources.
⚠ Exam Trap
Complete mode is often the correct answer for "rollback infrastructure to previous state" scenarios. Incremental mode is the safe default for ongoing deployments. Know when each is appropriate.
EX 12
Configure Application Insights for a Web App
Application Insights Monitoring
Lab Task

Create an Application Insights resource and connect it to an Azure Web App. Configure an availability test that pings the app's home page every 5 minutes from multiple locations. Create an alert that fires when availability drops below 80%. Write a basic KQL query to find failed requests in the last hour.

Step-by-Step Answer
  1. Create Application Insights resourceAzure Portal → Create resource → Application Insights. Select your resource group, region, and Log Analytics workspace. Create.
  2. Connect to Web AppWeb App → Settings → Application Insights → Turn on → Select your App Insights resource → Apply. The connection string is automatically added to app settings.
  3. Create Availability TestApp Insights → Availability → + Add Standard test. URL: your app's homepage URL. Test frequency: 5 minutes. Select multiple locations (e.g., East US, West Europe, Southeast Asia).
  4. Create Alert for availability dropAvailability test → Alert rules → + Create. Signal: Availability. Threshold: Less than 80%. Action group: create one that sends email. Severity: 1 (Error).
  5. Write KQL query for failed requests
// Failed requests in last hour
requests
| where timestamp > ago(1h)
| where success == false
| project timestamp, name, duration, resultCode, url
| order by timestamp desc
MCQ Version
A request fails in your microservices app. The error surfaces in Service C, which was called by Service B, called by Service A. Which Application Insights feature shows the complete call chain in a single view?
A Metrics Explorer — create a multi-resource chart
B Live Metrics — real-time performance stream
C End-to-end transaction details / Distributed tracing view
D Availability test results dashboard
C is correct. Application Insights propagates a correlation ID through all service calls. The end-to-end transaction view (accessed from a failed request) shows the complete call chain — Service A → B → C — with timing, dependencies, and the exact failure point. This is distributed tracing, one of the key exam objectives under instrumentation strategy.
EX 13
Integrate Azure Key Vault Secrets into a Pipeline
Key Vault Azure Pipelines Security
Lab Task

Store a database connection string as a secret in Azure Key Vault. Access this secret in an Azure Pipeline using the AzureKeyVault@2 task. Ensure the secret value is masked in pipeline logs. Verify the pipeline cannot access the secret if the service connection lacks Key Vault Reader permissions.

Step-by-Step Answer
  1. Create secret in Key VaultAzure Portal → Key Vault → Secrets → + Generate/Import. Name: db-connection-string. Value: your connection string. Create.
  2. Grant service connection accessKey Vault → Access control (IAM) → + Add role assignment. Role: Key Vault Secrets User. Assign to the service principal used by your Azure DevOps service connection.
  3. Use AzureKeyVault task in pipeline
steps:
  - task: AzureKeyVault@2
    inputs:
      azureSubscription: azure-connection
      KeyVaultName: my-keyvault
      SecretsFilter: db-connection-string   # Or '*' for all
      RunAsPreJob: true   # Available to all steps in job

  - script: echo "Connecting to database..."
    env:

Scan a Container Image and Push to Azure Container Registry
ACR Container Security Azure Pipelines
Lab Task

Create an Azure Pipeline that builds a Docker image, scans it for vulnerabilities using the MicrosoftSecurityDevOps@1 task, and pushes it to Azure Container Registry only if the scan passes. Tag the image with the pipeline build ID for traceability.

Step-by-Step Answer
  1. Pre-requisitesCreate an Azure Container Registry in the portal. Create a service connection to ACR in Azure DevOps (Project Settings → Service connections → Docker Registry → Azure Container Registry).
  2. Create complete pipeline
variables:
  imageRepository: myapp
  containerRegistry: myregistry.azurecr.io
  tag: $(Build.BuildId)   # Unique per run for traceability

steps:
  - # Step 1: Build the Docker image
    task: Docker@2
    inputs:
      command: build
      repository: $(imageRepository)
      tags: $(tag)

  - # Step 2: Scan the built image
    task: MicrosoftSecurityDevOps@1
    displayName: Container Vulnerability Scan
    inputs:
      categories: containers
      break: true   # Fail pipeline if vulnerabilities found

  - # Step 3: Push only if scan passed
    task: Docker@2
    inputs:
      command: push
      containerRegistry: acr-service-connection
      repository: $(imageRepository)
      tags: $(tag)
  1. Verify in ACRAzure Portal → Container Registry → Repositories. Your image appears with the build ID as the tag, providing full traceability to the pipeline run that produced it.
MCQ Version
Your pipeline builds a Docker image and scans it with MicrosoftSecurityDevOps@1 before pushing to ACR. A critical vulnerability is found. What happens if break: true is set on the scan task?
A The scan creates an alert but the pipeline continues and pushes the image
B The pipeline fails at the scan step — the push step never executes
C The pipeline pauses and waits for a security team member to approve continuing
D The image is pushed with a "vulnerable" tag appended automatically
B is correct. break: true causes the MicrosoftSecurityDevOps@1 task to fail the pipeline step when vulnerabilities above the configured threshold are found. Since the push step comes after the scan step and has the default condition: succeeded(), it is skipped — the vulnerable image never reaches ACR. This is the correct implementation of a security quality gate in a container build pipeline.
⚠ Exam Trap
Without break: true, the scan runs but only reports findings — it doesn't fail the pipeline. The image would still be pushed. Always set break: true when the scan should act as a quality gate, not just a reporting tool.
EX 18
Deploy ARM Template via Azure Pipeline
ARM Templates IaC Azure Pipelines
Lab Task

Create an ARM JSON template that provisions an Azure Storage Account, then deploy it via an Azure Pipeline using the AzureResourceManagerTemplateDeployment@3 task. The deployment must target a specific resource group, use incremental mode, and pass the storage account name as a parameter — not hardcoded in the template.

Step-by-Step Answer
  1. Create the ARM template (azuredeploy.json)Commit this to your repo root. ARM JSON always requires $schema, contentVersion, parameters, and resources.
// azuredeploy.json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "storageAccountName": {
      "type": "string",
      "minLength": 3,
      "maxLength": 24
    }
  },
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "2023-01-01",
      "name": "[parameters('storageAccountName')]",
      "location": "[resourceGroup().location]",
      "sku": { "name": "Standard_LRS" },
      "kind": "StorageV2"
    }
  ]
}
  1. Create the pipeline
steps:
  - task: AzureResourceManagerTemplateDeployment@3
    displayName: Deploy Storage Account ARM Template
    inputs:
      deploymentScope: Resource Group
      azureResourceManagerConnection: azure-wif-connection
      subscriptionId: $(subscriptionId)
      action: Create Or Update Resource Group
      resourceGroupName: rg-lab-demo
      location: eastus
      templateLocation: Linked artifact
      csmFile: azuredeploy.json
      deploymentMode: Incremental       # Safe: only adds/updates, never deletes
      overrideParameters: -storageAccountName mystoragelab$(Build.BuildId)
  1. Verify in Azure PortalResource Groups → rg-lab-demo → your storage account appears with the build ID suffix. Run the pipeline again — incremental mode means the existing resource is updated, not replaced.
MCQ Version
You deploy an ARM template in Incremental mode to a resource group that already contains a storage account not in your template. What happens to that storage account?
A It is left untouched — Incremental mode only adds or updates resources declared in the template
B It is deleted — ARM removes any resource in the group not present in the template
C The deployment fails — ARM requires all existing resources to be declared in the template
D It is tagged as "unmanaged" but remains running
A is correct. Incremental mode (the safe default) only reconciles resources that are declared in the template — it adds missing ones and updates existing ones. Resources already in the resource group but absent from the template are ignored entirely. Complete mode is the destructive alternative: it deletes any resource in the group not present in the template.
⚠ Exam Trap
The exam frequently tests Incremental vs Complete mode. Complete mode is the one that deletes undeclared resources — it is not the default and must be explicitly set with deploymentMode: Complete. Using Complete mode accidentally in a shared resource group will delete resources you didn't intend to touch.
EX 19
Deploy a Containerised App to AKS via Pipeline
AKS Kubernetes Azure Pipelines
Lab Task

Create a pipeline that builds a Docker image, pushes it to Azure Container Registry, then deploys it to an Azure Kubernetes Service cluster using a Kubernetes manifest. The deployment must use a rolling update strategy and pull the image from ACR using the build ID as the image tag. (Requires an Azure subscription with an AKS cluster and ACR.)

Step-by-Step Answer
  1. Pre-requisitesCreate an AKS cluster and ACR in the Azure Portal (or via CLI). Attach ACR to AKS: az aks update --name myCluster --resource-group myRG --attach-acr myRegistry — this grants AKS the AcrPull role so pods can pull images without a Kubernetes secret.
  2. Create the Kubernetes manifest (k8s/deployment.yml)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  strategy:
    type: RollingUpdate       # Zero-downtime: replaces pods one at a time
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp
          image: myregistry.azurecr.io/myapp:$(Build.BuildId)
          ports:
            - containerPort: 80
  1. Create the pipeline
stages:
  - stage: Build
    jobs:
      - job: BuildAndPush
        pool:
          vmImage: ubuntu-latest
        steps:
          - task: Docker@2
            displayName: Build and Push to ACR
            inputs:
              command: buildAndPush
              containerRegistry: acr-service-connection
              repository: myapp
              tags: $(Build.BuildId)

  - stage: Deploy
    dependsOn: Build
    condition: succeeded()
    jobs:
      - deployment: DeployToAKS
        environment: aks-production       # Enables approval gates + rollback
        strategy:
          runOnce:
            deploy:
              steps:
                - task: KubernetesManifest@1
                  displayName: Deploy to AKS
                  inputs:
                    action: deploy
                    connectionType: azureResourceManager
                    azureSubscriptionConnection: azure-wif-connection
                    azureResourceGroup: myRG
                    kubernetesCluster: myCluster
                    manifests: k8s/deployment.yml
                    containers: myregistry.azurecr.io/myapp:$(Build.BuildId)
  1. Verify the rolloutAfter the pipeline runs, check the deployment: kubectl get pods shows 2 running pods with the new image. kubectl rollout status deployment/myapp confirms a clean rolling update with no downtime.
MCQ Version
Your AKS deployment manifest uses strategy.type: RollingUpdate with maxUnavailable: 0 and maxSurge: 1. The cluster currently runs 2 replicas. How does Kubernetes update the pods?
A Both old pods are terminated first, then 2 new pods are created — brief downtime occurs
B One old pod is terminated before the new one starts — always 1 pod available during update
C A new (surge) pod starts first, then one old pod is terminated — at least 2 pods always available, zero downtime
D All pods are replaced simultaneously using a blue/green switch
C is correct. With maxUnavailable: 0, Kubernetes never terminates an old pod until a new one is healthy and ready. With maxSurge: 1, it spins up one extra pod (3 total temporarily) before removing an old one. This cycle repeats until all pods run the new version — guaranteeing zero downtime. The total pod count temporarily exceeds the desired 2 during the update, which is the surge.
⚠ Exam Trap
Using a deployment job (not a regular job) in Azure Pipelines is required to target an environment. Only deployment jobs unlock environment-level approval gates, deployment history tracking, and rollback in the Azure DevOps UI. A regular job that deploys to AKS bypasses all of these controls.
